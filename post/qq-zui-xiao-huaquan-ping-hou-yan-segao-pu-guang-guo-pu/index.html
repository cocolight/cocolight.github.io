QQ 最小化/全屏后颜色「高曝光」过曝

2026-10-18 • 5 分钟阅读 • fedora • linux · qq · electron

现象：QQ（Linux NT 版，Electron/Chromium 内核）最小化后再全屏、或窗口状态切换后， 画面整体变得「高曝光」、偏亮、过饱和（washed out / tinted light / over-saturated）。 这是应用与合成器的色彩管理交互 bug，不是显示器或硬件故障。

一、根因（已查实）

这是 Chromium/Electron 与 KWin 的 Wayland 色彩管理协议（wp_color_manager_v1）交互缺陷，社区已有大量实证：

  • ArchWiki（Chromium Tips and Tweaks） 明确记载：

    “Under KWin with Wayland colors appears to be washed up compared to Firefox. The workaround is to run chromium with flag --disable-features=WaylandWpColorManagerV1.”

  • KDE Bug 510671（Chromium windows tinted light）：拖动窗口时颜色正常、放下后变浅—— 因为窗口合成状态变化触发了不同的色彩处理路径，与「最小化→全屏变过曝」机制一致。

  • 多家 Electron 应用（Spotify、Signal、Beekeeper Studio）在 KDE Wayland 上报告过同类过饱和/过曝， 统一的根因是 Chromium 在 wp_color_manager_v1 协商时错误地以更高亮度/更广色域渲染（漏掉 transfer function 转换）。

  • 本机确证：/usr/share/applications/qq.desktop 的 Exec 行已显式启用原生 Wayland：

    Exec=/opt/QQ/qq %U --enable-features=UseOzonePlatform --ozone-platform=wayland --enable-wayland-ime

    → QQ 跑在 Electron 原生 Wayland Ozone 后端，会参与 KWin 的色彩管理协议协商，从而触发该 bug。

二、为什么「最小化→全屏」才触发

KWin 的色彩管理在窗口的 surface 提交 / 角色变化（最小化→恢复、全屏切换、输出目标变化）时， 会重新评估并应用输出色彩空间。这个重新协商的时机正是 Chromium 出错的地方—— 它以错误的亮度/色域（把 SDR 当广色域或漏掉 gamma 转换）重新提交帧，于是整体「高曝光」。 状态稳定后可能持续错误，直到下一次状态切换再次触发协商。

注：本机 kwinrc 的 Brightness=0.43 是显示亮度控制，不是色彩管理本身； Plasma 6 默认开启色彩管理（Color accuracy 设置），与本 bug 共存。

三、解决方案

方案 A（推荐）：关闭有问题的色彩管理协议，保留 Wayland 原生模式

在 QQ 启动参数里加 --disable-features=WaylandWpColorManagerV1。 用用户级 override（不会被 QQ 更新覆盖系统 /usr/share 文件）：

mkdir -p ~/.local/share/applications
cp /usr/share/applications/qq.desktop ~/.local/share/applications/qq.desktop

编辑 ~/.local/share/applications/qq.desktop，把 Exec 行改为：

Exec=/opt/QQ/qq %U --enable-features=UseOzonePlatform --ozone-platform=wayland --enable-wayland-ime --disable-features=WaylandWpColorManagerV1

（即在原参数末尾追加 --disable-features=WaylandWpColorManagerV1，保留 %U 占位符。）

应用级刷新（可选）：

update-desktop-database ~/.local/share/applications 2>/dev/null || true

完全退出 QQ（含托盘后台）→ 从启动器重新打开 才能生效。

方案 B（备选）：让 QQ 走 XWayland，彻底不参与 Wayland 色彩管理

把 Exec 行改为（注意移除 --enable-wayland-ime，X11 下不需要）：

Exec=/opt/QQ/qq %U --ozone-platform=x11

代价：失去原生 Wayland 输入法（--enable-wayland-ime）与部分 HiDPI/合成特性； 若你依赖 Fcitx5/IBus 输入法，方案 A 更稳妥。

方案 C（系统级缓解，效果次于 A）

系统设置 → 显示与监控 → 色彩管理：

  • 给显示器指定一个纯 sRGB 色彩描述文件；

  • 切换「颜色准确度」选项（Prefer efficiency / Prefer color accuracy）。

注意：KDE Bug 510671 报告两种选项下均可能复现，故应用级 flag（方案 A）是最可靠的修复。

四、验证修复是否生效

  1. 重启 QQ（方案 A/B 后）。

  2. 连续做「最小化 → 恢复 → 全屏 → 退出全屏」多次。

  3. 观察深色区域（如聊天背景、黑色文字块）是否恢复正常黑度、不再发灰发亮。

  4. 若仍过曝：确认用户级 qq.desktop 生效（which/启动器来源），并确认 QQ 进程确实带该 flag：

ps aux | grep -i qq | grep -o 'WaylandWpColorManagerV1'

有输出即参数已加载。
