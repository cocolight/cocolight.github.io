一、目标与验收标准

1.1 目标

从机顶盒与运营商平台的网络交互中，提取“频道名 :left_right_arrow: 播放地址”的完整映射，并生成播放器可直接使用的播放列表。

拆解为三层可验证的子目标：

层 要拿到的东西 为什么
认证层 机顶盒如何通过运营商认证（账号 / 令牌 / 会话） 没有有效会话，服务器不下发频道表
数据层 频道表原始响应体（含每个频道的 ID、名称、播放地址） 这是唯一的信息源
交付层 播放列表（m3u8）与结构化清单（CSV） 最终可用产物

注意“目标”与“结果”的区别。目标只描述“要抓什么类型的流量、要得到什么结构的数据”，
不预设在频道数量。频道数与具体频道名是执行结果，写在第五章。

1.2 验收标准

一条链、五个环节，每一环都有可执行的判据。任何一环不达标，最终产物就不可信。

# 环节 验收动作 通过判据
1 链路串通 brctl showmacs <bridge>（或交换机 SPAN 配置） 桥两条腿都学到 MAC
2 抓包有效 capinfos X.pcap + 源 MAC 分布统计 包数/时长合理，目标设备 MAC 出现次数 > 0
3 会话完整 tshark -Y "http.request" 列全部 HTTP 请求 认证链全部 200，isSucessed=true
4 数据到达 检查频道接口响应体 ChannelCount 非 0，且能搜到频道条目
5 产物正确 用解析脚本端到端复跑 条目数 == 服务器返回的 ChannelCount

第 4 环是最容易被忽略的：“抓到了 HTTP 200”不等于“拿到了频道数据”。
服务器完全可能回一个 685 字节的空壳（详见 7.4）。

二、环境与拓扑

2.1 设备与角色

角色 关键参数 作用
运营商光猫 有一个独立的 IPTV 口（Bridge 模式，绑定 VLAN） IPTV 流量的物理出口
IPTV 机顶盒 双栈：LAN 侧有内网地址，IPTV 侧有业务地址 被分析对象
接入交换机 非网管、不支持 802.1Q、无镜像口 限制条件（决定了抓包方案）
软路由 多网口 x86 设备，可作透明网桥 抓包点载体
分析机 运行 Wireshark / tshark 离线分析

机顶盒双地址必须分清（这是最容易填错 BPF 的地方）：

侧 地址类型 说明
LAN 侧 内网地址（如 192.168.x.x） 走路由器上网，控制面也可能在这里
IPTV 侧 运营商业务地址（如 172.203.x.x） 网关是运营商设备，数据面组播在这里

2.2 连接关系与拓扑演进

IPTV 链路的连接方式直接决定能不能抓到单播。三种典型形态：

形态一：机顶盒直连光猫 IPTV 口

 光猫 IPTV 口 ──── 机顶盒

抓包必须串在中间，无法旁路。

形态二：经交换机（最常见，也最容易踩坑）

 光猫 IPTV 口 ──┐
                ├── 交换机 ──┬── 机顶盒
                │            └── 抓包机（旁路口）← 抓不到单播

二层交换机做“源 MAC 学习 + 定向转发”，机顶盒与光猫之间的单播只在它们各自那一对端口间走，
旁路第三个口只能看到广播 + 组播。

形态三：软路由替代交换机（本次采用）

 光猫 IPTV 口 ── eth1 ─┐
                       ├── br-iptv（二层透明网桥）
 机顶盒       ── eth2 ─┘
 管理机       ── eth3 ──── br-lan（另一个网段，SSH 不掉线）

把链路串进软路由，单播就必然穿透网桥，eth1 上两个方向都能看到。

2.3 抓包点选择：决策树

先问一个问题：你要抓的是单播，还是只需要广播/组播？

 要抓的是单播吗？
 ├─ 是 → 必须"在链路中间"
 │        ├─ 有管理型交换机 → 用 SPAN 端口镜像（首选：零侵入、零风险）
 │        └─ 没有          → 用软路由/一台 Linux 做 in-line 透明网桥
 └─ 否（只抓广播/组播）→ 旁路口也能凑合

2.3.1 方案一：交换机端口镜像（SPAN）

首选方案。不动任何接线，只在交换机上做一次配置。

         ┌──────────── 管理型交换机 ────────────┐
 光猫 ── port1                              port2 ── 机顶盒
                     port3 ── 抓包机
                     ↑
               port2 设为 SPAN 源，port3 设为 SPAN 目标
               （源端口收发的全部流量，从目标口原样复制一份）

要点：

  • 镜像方向要选 both（双向），只镜 RX 或只镜 TX 会漏一半会话；
  • 目标口通常不能再承载正常业务；
  • 交换机必须支持 SPAN（非网管交换机做不到 —— 本次的硬约束）。

2.3.2 方案二：软路由透明网桥

交换机不支持镜像时的最优解，零硬件成本，代价是改接线（可能短暂断网）。

 光猫 ── eth1 ─┐
               ├── br-iptv  ← 二层网桥，桥本身不做三层
 机顶盒 ── eth2 ┘
 抓包机 ── eth3 ──── br-lan（独立网段，SSH 不失联）

透明网桥三要素，缺一不可：

要素 为什么 配置
桥不做三层 桥接口一旦有 IP 就成了“路由器”，可能改包 / 改路径 桥只做二层；如确需 IP，不要把它加进防火墙 zone
关闭 IGMP snooping 开启后会“按需”剪枝组播，可能丢帧 option igmp_snooping '0'
关闭 bridge-nf-call-* 否则桥接帧会被送进 netfilter 的 forward 链，policy drop 直接丢 置 0 / 确认 br_netfilter 未加载

实际配置（OpenWrt / ImmortalWrt，UCI 写法）：

 # ① 建立网桥设备，指定成员口
 #    ipv6=0 顺手关掉，避免 IPv6 邻居发现干扰
 uci set network.iptv_br=device
 uci set network.iptv_br.name='br-iptv'
 uci set network.iptv_br.type='bridge'
 uci set network.iptv_br.ports='eth1 eth2'
 uci set network.iptv_br.igmp_snooping='0'    # ★ 要素二
 uci set network.iptv_br.stp='0'
 uci set network.iptv_br.ipv6='0'
 uci commit network
 ​
 # ② 让网桥生效
 /etc/init.d/network reload

验证三要素是否到位：

 # 要素二：确认 igmp_snooping 已关（应为 0）
 cat /sys/class/net/br-iptv/bridge/multicast_snooping
 # 输出：0
 ​
 # 要素三：检查 bridge-nf 三个开关
 # 全为 0 或文件不存在（NA）都算通过——NA 表示 br_netfilter 未加载，等效放行
 for f in iptables ip6tables arptables; do
   printf '%s = ' "$f"
   cat /proc/sys/net/bridge/bridge-nf-call-$f 2>/dev/null || echo "NA"
 done
 # 输出（本次实测）：
 #   iptables = NA
 #   ip6tables = NA
 #   arptables = NA

NA 为什么也算通过：bridge-nf-call-* 只有在 br_netfilter 模块加载后才存在。
文件不存在 = 模块没加载 = 桥接帧根本不会进 netfilter → 天然放行。

黄金判据 —— 抓包前必做：

 # 作用：打印网桥转发表，看每个端口学到了哪些 MAC
 brctl showmacs br-iptv

 # 输出（本次实测，已脱敏）：
 port no  mac addr            is local?  ageing timer
   1      0c:12:62:b4:f4:10   no          0.00    ← eth1 侧，光猫       ★ 必须有
   2      48:57:02:25:bb:e3   no          0.15    ← eth2 侧，机顶盒     ★ 必须有
   1      60:be:b4:02:68:0f   yes         —       ← 网桥自己的 MAC，忽略

怎么读：

  • port no 对应成员口（1=eth1，2=eth2）；
  • is local? = no 的条目才是外部设备（yes 是网桥自身）；
  • 两条腿都学到 MAC，才证明单播二层转发已打通。缺任一条，后面全白干；
  • ageing timer 是老化倒计时（秒），越小说明越活跃。
    若看到 300+ 说明该设备很久没发包了。
 # 若 FDB 里没有目标设备，先确认接口本身有载波
 ip -br link show eth1 eth2
 # 输出示例：
 # eth1     UP    60:be:b4:02:68:0f <...>     ← UP 且有 MAC，正常
 # eth2     DOWN  60:be:b4:02:68:10 <NO-CARRIER,...>   ← ★ NO-CARRIER，机顶盒没接上

:warning: NO-CARRIER 是最常见的“抓不到”原因 —— 接口没插线/对端没上电，
此时“能抓到流量”是假象（收到的是其他口泛洪的镜像）。

2.3.3 为什么“旁路”不行（原理）

普通二层交换机做两件事：

  1. 源 MAC 学习 —— 收到帧，把“源 MAC :left_right_arrow: 入端口”记进 FDB 表；
  2. 定向转发 —— 查目的 MAC，只从对应端口发出（查不到才泛洪）。
         ┌──────────── 交换机（非网管）────────────┐
 光猫 ──── port1                                port2 ──── 机顶盒
                   port3 ──── 抓包机  ← 在这里抓

机顶盒 :left_right_arrow: 光猫的单播只在 port1 :left_right_arrow: port2 之间走，永不出现于 port3。
port3 上只剩广播（ARP / DHCP 部分）和组播（视频流）。

控制面 vs 数据面的可见性对照：

层面 典型协议 单播/组播 旁路可见
控制面 DHCP、HTTP（认证、频道表） 单播 :cross_mark: 看不到
数据面 频道视频流 239.x.x.x:4120 组播 :check_mark_button: 看得到

→ 旁路抓包的典型结果是：能列出组播地址，永远拿不到频道名
（频道名在单播的 HTTP 响应里）。

三、抓包工具选型

3.1 工具优先级判据

优先级 来源 定义
1 成品软件 Wireshark / tshark / tcpdump 等成熟工具
2 可获取的成熟方案 本地没有，但能方便下载安装的包（如 opkg install tcpdump）
3 广泛使用的开源项目 GitHub 上被广泛使用、有社区维护的项目
4 自建脚本（最后手段） 仅当 1–3 全部不可用

自建的触发条件（三条同时满足才动手）：

  1. 无成品软件可用，且无被广泛使用的成熟开源项目；
  2. 已有的替代方案安装成本过高或根本装不上（如精简固件的包管理器为空）；
  3. 自建方案能覆盖“持续运行 + 全量落盘 + 可重复离线分析”三项需求。

反例：仅仅因为“本机没装 Wireshark”就自建抓包脚本 —— 属于滥用。
正确做法是先评估安装成本。

3.2 候选工具对照

工具 形态 优势 局限
Wireshark（GUI） 桌面成品 强大、可视化、协议解码全 需图形环境
tshark 命令行 同为 Wireshark 引擎，可脚本化 需本机安装
tcpdump 命令行 极轻量，路由器固件常自带 只能抓/筛，不解析协议
sshdump（Wireshark 远程） 需远端 dumpcap 图形界面直接抓远端 远端必须有 dumpcap
自建 SSH 流式脚本 自写 远端零改动 需自己处理缓冲/截断

3.3 选型过程（本项目实例）

 ① 首选 Wireshark 的 sshdump 远程抓包
    └─ ❌ 远端是精简固件的 OpenWrt：无 dumpcap，包管理器源为空，装不上
 ② 退一步：用远端 tcpdump（固件自带）
    └─ ✅ 有
 ③ 但远端抓完的文件怎么拉回？
    ├─ SFTP ── ❌ 精简固件的 dropbear 无 sftp 子系统
    └─ ✅ 用 SSH exec 把 tcpdump 输出流式接回本地

最终做法：本地跑一个脚本，SSH 到路由器执行
tcpdump -i <iface> -nn -U -s 0 -w - <bpf>，
-w - 表示把 pcap 写到 stdout，通过 SSH 通道把字节流直接落到本地文件。

远端命令逐参数拆解：

 tcpdump -i <iface> -nn -U -s 0 -w - "<BPF>" 2>/dev/null
参数 含义 为什么必需
-i <iface> 指定接口 必须真实接口名；某些内核不支持 -i any 的混杂模式
-nn 不做名称解析（IP、端口都保持数字） 避免 DNS 反查拖慢抓包
-U packet-buffered，收到即写 默认会攒满 4KB 才写；不加以至流式传输没有实时性
-s 0 抓完整包（snaplen 无限） 默认只抓 96 字节，HTTP 响应体直接被截断，无法解析
-w - pcap 写到 stdout 配合 SSH 通道/管道，是流式接回的关键
"<BPF>" 抓包过滤器 见第四章，建议 ip or arp 全抓
2>/dev/null 丢弃 stderr 避免警告混进 pcap 字节流污染文件

等价的最小实现（不用脚本，纯命令行）：

 # 在本地执行：把远端的 tcpdump 输出直接落成本地 pcap
 # -T 禁用伪终端分配，避免 dropbear 把二进制流当终端输出做换行转换
 ssh root@<router> "tcpdump -i eth1 -nn -U -s 0 -w - 'ip or arp'" > local_capture.pcap

:warning: 必须加 -T（或 -tt）：

 ssh -T root@<router> "tcpdump ... -w -" > local_capture.pcap

不加的话，SSH 会分配伪终端并把 \n 转成 \r\n，
写出的 pcap 会因字节膨胀而损坏。

脚本版（Python + paramiko）的核心逻辑：

 # 伪代码：建立 SSH 后开一个 session channel，把 stdout 字节流写入本地文件
 chan = client.get_transport().open_session()
 chan.settimeout(seconds)
 chan.exec_command("tcpdump -i eth1 -nn -U -s 0 -w - 'ip or arp' 2>/dev/null")
 ​
 with open(out, "wb") as f:
     while True:
         data = chan.recv(65536)
         if not data:
             break
         f.write(data)      # ★ 二进制模式写入，绝不能是文本模式

这条路的价值：远端零改动、本地拿到标准 pcap，可用任意 tshark 过滤器反复分析。

3.4 命令行速查的通用约定

后续所有示例遵循以下约定，请先读完本节再看示例。

环境前提

Wireshark 命令行工具（tshark / capinfos / editcap）默认不在 PATH，先加进去：

 # Windows（Git Bash）：Wireshark 默认装在 Program Files
 # 路径含空格，必须加引号；注意用 /d/ 而不是 D:\
 export PATH="$PATH:/d/Program Files/Wireshark"
 ​
 # Linux / macOS
 export PATH="$PATH:/usr/sbin:/usr/local/bin"

验证工具链是否就绪：

 tshark -v
 # 输出：TShark (Wireshark) 4.6.9 (v4.6.9-0g2d548b197c75)

占位符约定

占位符 含义 本次实例
<iface> 抓包的物理接口名 eth1
<bridge> 网桥接口名 br-iptv
X.pcap 抓包文件名 eth1_stb_20261003.pcap
<STB-MAC> 机顶盒 MAC 48:57:02:25:bb:e3
<N> TCP 流号 20

文中出现具体值的地方均标注“（本次实测）”。你的环境一定会不同，
照抄前先替换成自己的值。

tshark 四个核心参数

参数 作用 记忆点
-r X.pcap 读取已有文件 read
-w Y.pcap 写出到文件 write
-Y "<表达式>" 显示过滤器（分析时筛选） 首字母大写，语法如 http.request
-T fields -e <字段> 输出指定字段而非完整解码 便于 sort / uniq / awk
-q -z <统计> 只出统计，不逐包打印 用于体检类输出

★ 最容易混的点：-Y 和 BPF 不是一回事

BPF（抓包过滤） 显示过滤器（tshark -Y）
用在哪 tcpdump 抓包时 tshark 分析时
语法 ip or arp、port 67 http.request、tcp.stream==20
大小写 关键字小写 协议名字段名有大小写规范
能否事后改 :cross_mark: 抓的时候漏了就没救 :check_mark_button: 可对同一文件反复换条件 
 # ❌ 错误示范：把显示过滤器语法喂给 tcpdump
 tcpdump -i eth1 "http.request"        # 报语法错，抓不到东西
 ​
 # ✅ 正确：tcpdump 用 BPF，tshark 用显示过滤器
 tcpdump -i eth1 "ip or arp"
 tshark  -r X.pcap -Y "http.request"

抓包用 BPF，分析用 -Y。抓包时尽量放宽（宁可全抓），分析时再精确筛。

四、抓包流程总览

4.1 流程线

 ① 确认链路可抓  →  ② 布置抓包点  →  ③ 验证抓包点有效
                                             ↓
             ⑥ 定位控制面  ←  ⑤ 落地体检  ←  ④ 执行抓包
                     ↓
             ⑦ 切流导出对象  →  ⑧ 解析成结构化清单  →  ⑨ 生成播放列表

4.2 每步一句话

步 做什么 一句话
① 确认链路 机顶盒能否在链路上独立 DHCP 拿到 IPTV 侧地址
② 布置抓包点 SPAN 优先，否则软路由透明网桥
③ 验证有效性 看到目标设备的 MAC 才算抓对地方
④ 执行抓包 全抓 + 覆盖关键动作（重启 → 认证 → 拉列表 → 切台）
⑤ 落地体检 先看包数/时长/协议分布，再谈解析
⑥ 定位控制面 从 DHCP 到认证到列表接口，串出完整会话链
⑦ 切流导出 先按流切分，再导出 HTTP 对象（自动解压）
⑧ 解析 从响应体抽字段 → 结构化清单
⑨ 生成列表 组装成播放器可用的 m3u8

五、分步流程详解

表中“实际拿到”列取自本次实战；“差异分析”说明为什么与预期不同。

5.1 抓包参数（本次实测）

参数 值 理由
接口 eth1（桥的光猫侧成员口） 选成员口而非桥设备，两个方向都在
时长 360 s 覆盖“断电重启 → 认证 → 开频道列表 → 切台”全过程
BPF ip or arp 绝不按端口过滤（会漏组播/非标准端口）
结果 277604 包 / ~356 MB —

完整抓包命令（逐参数注释）：

 # 在软路由上执行（或经 SSH 流式接回本地，见 3.3）
 tcpdump \
   -i eth1 \          # 桥的光猫侧成员口：两个方向的单播都经过它
   -nn \              # 不做名称解析，保持数字形式，避免 DNS 反查拖慢
   -U \               # packet-buffered：收到即写，不等 4KB 缓冲
   -s 0 \             # snaplen=0 表示抓完整包（默认 96B 会截断 HTTP 响应）
   -w - \             # pcap 写 stdout（流式接回时用）；本地抓则写文件名
   'ip or arp'        # ★ BPF：全抓 IP + ARP，不按端口过滤

为什么 BPF 是 ip or arp 而不是按端口：

 #

:cross_mark: 反面示范：按“常见 IPTV 端口”过滤
 tcpdump -i eth1 “port 80 or port 443 or port 554 or port 4120”
 #   问题：漏掉非标准端口（运营商改端口就全废）、漏掉 DHCP（67/68）、漏掉 ARP
 ​
 # ✅ 正确：全抓，分析时再筛
 tcpdump -i eth1 “ip or arp”
 #   代价：文件大（本次 356MB）
 #   收益：一次抓全，事后可用任意过滤器反复分析——抓包机会往往只有一次

如果只想抓单播（排除组播以免文件过大）：

 # 抓"非组播"的 IP 流量 + ARP
 tcpdump -i eth1 "ip and not dst net 239.0.0.0/8 or arp"

:warning: BPF 语法坑：ip and 239.0.0.0/8 这种写法静默匹配不到任何东西，
必须写成 dst net 239.0.0.0/8（明确 net 关键字 + 方向）。

5.3 执行抓包的动作序（关键）

抓包必须覆盖完整开机流程，顺序建议：

1. 先把 tcpdump 跑起来（进入等待）
2. 再给机顶盒断电重启          ← 不能反过来
3. 等待认证完成（观察组播流出现）
4. 在电视上打开频道列表 / 切台
5. 跑满时长后停止

时机错位是“抓到包但没频道表”的最常见原因 —— 认证是一次性的，错过就没有。

可执行的时序骨架（手动操作也照这个顺序）：

# ── 第 1 步：先起抓包（SSH 流式接回，放后台跑） ──
# 3600s 是兜底上限，实际靠 Ctrl-C 或 kill 结束
ssh -T root@192.168.100.1 \
    "tcpdump -i eth1 -nn -U -s 0 -w - 'ip or arp'" \
    > capture.pcap &
CAP_PID=$!

# 等 2 秒，确认 tcpdump 真的起来了（文件在增长）
sleep 2
ls -l capture.pcap     # 大小应为几 KB 并在增长；若是 0 说明没抓上

# ── 第 2 步：此时才给机顶盒断电重启（物理操作） ──
echo "现在去重启机顶盒，然后等它开机完成、打开频道列表、切一次台"

# ── 第 3 步：观察控制面是否出现（可选，实时验证） ──
# 另开一个终端，边抓边看（同样连路由器）
# ssh root@192.168.100.1 "tcpdump -i eth1 -nn 'tcp port 80 or tcp port 33200' -c 20"

# ── 第 4 步：跑满后停止 ──
sleep 360
kill $CAP_PID

# ── 第 5 步：立刻体检，确认这包有没有价值 ──
capinfos capture.pcap

自检点：

  • 第 1 步后必须确认文件在增长，否则可能接口名写错/无载波；
  • 若抓完发现“没有 HTTP 请求”，说明错过了开机窗口，重来一次；
  • 不要在抓包开始前就重启机顶盒 —— 这是最常见的失误。

6.1 通用分析链

capinfos 体检（包数/时长/接口）
  → 源 MAC 分布 / 协议层次（谁在说话）
  → 按协议分组：DHCP / ARP / HTTP / IGMP / 组播

# 作用：统计每个源 MAC 发了多少包，按数量倒序
# 原理：-e eth.src 只输出源 MAC 字段 → sort 排序 → uniq -c 计数 → sort -rn 按数量倒排
tshark -r X.pcap -T fields -e eth.src 2>/dev/null | sort | uniq -c | sort -rn

# 输出（本次实测）：

  26509 48:57:02:25:bb:e3   ← ★ 机顶盒！出现即证明抓到目标流量
     32 4c:ac:0a:dc:6c:9d   ← 零散第三方设备

怎么读：

  • 目标设备（机顶盒）的 MAC 必须出现，且数量可观（本次 26509 包）；

  • 出现但只有几条 → 只抓到广播/邻居发现，没抓到会话。

tshark -r X.pcap -q -z io,phs 2>/dev/null

# 输出（本次实测，节选）：

怎么读：

# bootp.option.dhcp 是消息类型编码：1=Discover 2=Offer 3=Request 5=ACK 6=NAK
tshark -r X.pcap -Y "bootp" -T fields \
       -e frame.number -e ip.src -e ip.dst -e bootp.option.dhcp 2>/dev/null

# 输出（本次实测）：
99400   0.0.0.0          255.255.255.255  3   ← Request
99411   172.203.68.1     255.255.255.255  6   ← ★ NAK（拒绝！）
100270  0.0.0.0          255.255.255.255  1   ← Discover
100278  172.203.68.1     172.203.69.247   2   ← Offer（分配地址）
100279  0.0.0.0          255.255.255.255  3   ← Request

怎么读：

  • 完整成功链 = 1 → 2 → 3 → 5（Discover → Offer → Request → ACK）；

6.2.1 ★ 定位关键流的正确姿势（不要硬编码流号）

很多教程直接写 tcp.stream==20，这是不可复现的 —— 流号取决于抓包起点，
换一次抓包就变了。正确做法是先查出流号：

# 第一步：按 URI 关键字反查这条会话属于哪个 TCP 流
tshark -r X.pcap -Y 'http.request.uri contains "getchannellist"' \
       -T fields -e frame.number -e tcp.stream -e ip.dst -e http.request.uri 2>/dev/null

# 输出（本次实测）：
101428  20  10.11.37.165      /EPG/jsp/getchannellistHWCU.jsp
101448  20  172.203.69.247    /EPG/jsp/getchannellistHWCU.jsp

→ 得到流号 20。然后再用它切流：

# 第二步：用查到的流号切出这条会话（-w 写出新 pcap）
tshark -r X.pcap -Y "tcp.stream==20" -w _s20.pcap

可复现性的关键：把“查流号”和“切流”分成两步。
下次换一份 pcap，第一条命令会给出新的流号，流程不变。

6.2.2 ★ 确认拿到的是“真频道表”而不是空壳

这是最容易误判的地方：HTTP 200 不代表有数据。

# 作用：列出该流的所有响应，看状态码 + 内容长度 + 是否压缩
tshark -r X.pcap -Y "tcp.stream==20 && http.response" -T fields \
       -e frame.number -e http.response.code -e http.content_length \
       -e http.content_encoding 2>/dev/null

# 输出（本次实测）：
101416  200  685     ← ⚠️ 只有 685 字节，且未压缩 = 空壳！
101420  200  3067
101426  200          gzip   ← 压缩响应，长度未知（需解压后才知道）
101448  200          gzip   ← ★ 这才是真频道表（解压后 190697 B）
101452  200  494
101462  200  6658

怎么读 —— 三个判据：

判据 空壳 真频道表
content_length 极小（本次 685 B） 大，或显示为空（因 gzip 无法预知）
content_encoding 无 gzip
解压后搜关键字 搜不到 ChannelName 能搜到 CusetConfig('Channel'

决定性验证（对导出体做关键字检索）：

# 从导出的响应体里搜频道表特征串
grep -c "CUSetConfig('Channel'" _o20/getchannellistHWCU*.jsp
# 输出：1（找到）表示真有频道数据；0 表示是空壳

⚠️ 本次实例的特殊之处：tcp.stream==20 这条流里，
同一条 URI 被请求了两次 —— 101416 返回 685 字节空壳，
101448 返回 gzip 真表。
只看到前一条就下结论“没抓到频道表”，是最常见的误判。
必须把该流的所有响应列出来逐一判断。

6.4 常见误判与陷阱

# 陷阱 现象 正确做法
1 -c 是“读取上限” -c 30 只读前 30 包 → 误判“一条都没抓到” 要计数别用 -c
2 BPF 按端口过滤 漏掉组播/非标准端口 用 ip or arp 全抓，离线筛
3 导出对象不切流 只导出一个对象 / 跨流聚合 先 -Y "tcp.stream==N" 切流
4 --export-objects 跨流聚合 同名对象被合并，误认为来自某条流 导出结果不能反推“来自哪条流”
5 IsHDChannel 当高清判据 与频道名矛盾（高清频道标 SD） 用**频道名是否含“高清”**判断
6 gzip 响应当乱码 导出内容不可读 Wireshark「导出对象」自动解压
7 PSI 不校验 CRC32 把 ES 数据里的随机字节当 table_id，得出假频道表 任何 PSI/私有 section 解析，必须 CRC32==0 校验
8 协议名字写错 查 MPEG-TS 用 mpegts 查不到 tshark 里是 MP2T，字段 mpeg_pat.*
9 VLAN 判断靠猜 — tshark -T fields -e vlan.id，空 = 无 tag
10 忘记看接口链路状态 在 NO-CARRIER 口上“抓到”了流量 先 ip -br link 确认 UP + carrier

第 10 条代价最大：NO-CARRIER 接口上“抓到”的流量全是交换机/网桥泛洪的镜像，
不是那条链路真实经过的流量。看到“抓到数据”不代表抓对了地方。

按根因分类，便于定位同类问题。

7.1 抓包点类（最高频）

问题 现象 根因 解决
只能看到组播，无认证/频道表 抓到大量 239.x.x.x:4120，HTTP 会话为 0 抓包点在旁路，单播不经过 移到链路中间（SPAN 或透明网桥）
网桥上抓包漏单播 抓 br-iptv 只看到部分流量 bridge hairpin + igmp_snooping=1 在桥接层消费 抓物理成员口（如 eth1），不抓桥设备
在错误接口上抓 “抓到流量”但分析发现全是别的设备 NO-CARRIER 口上收到的是泛洪镜像 先 ip -br link + brctl showmacs 确认

“抓物理口不抓桥设备”的对照验证：

# 同一目标会话，在两个接口上分别统计，差异立现
# ① 在物理成员口上：能看到完整的双向单播
tshark -r physical.pcap -Y "http.request" -T fields -e frame.number | wc -l
# 输出：若干条 HTTP 请求（控制面完整）

# ② 在网桥设备上：会话被桥接层消费，只剩一部分
tshark -r bridge.pcap -Y "http.request" -T fields -e frame.number | wc -l
# 输出：明显更少，或为 0

判断当前流量“到底是谁的”（识别泛洪镜像）：

# 统计每个源 MAC 的包数，确认目标设备是否真的存在
tshark -r X.pcap -T fields -e eth.src | sort | uniq -c | sort -rn | head -5
# 若目标设备 MAC 完全没出现 → 你抓的是别人泛洪过来的镜像，抓包点错了

# 抓包时带上 -e 直接看链路层地址（tcpdump 的 -e 显示源/目的 MAC）
tcpdump -i eth1 -nn -e -c 10

或者对已有 pcap 提取链路层地址（本次实测）：

# -e eth.src -e eth.dst 同时输出源/目的 MAC，配合 ip 字段看归属
tshark -r X.pcap -c 5 -T fields \
       -e eth.src -e eth.dst -e ip.src -e ip.dst 2>/dev/null

# 输出（本次实测）：
0c:12:62:b4:f4:10  01:00:5e:7d:02:42  10.11.43.98  239.125.2.66
0c:12:62:b4:f4:10  01:00:5e:7d:02:42  10.11.43.98  239.125.2.66

怎么读：

  • 目的 MAC 01:00:5e:... 是组播 MAC（IPv4 组播映射：01:00:5e + 地址低 23 位）；
  • 源 MAC 是光猫 0c:12:62:b4:f4:10，说明这路组播是运营商侧推过来的；
  • 若源 MAC 是机顶盒，说明方向相反。

:warning: 本次踩过的坑：多个 IP（运营商网关 172.203.68.1、业务地址 10.11.43.98、
门户地址）共享同一个源 MAC，都来自光猫。
如果不看 MAC，会误以为 10.11.43.98 是机顶盒的地址 —— 实际它是光猫持有的业务地址。
抓包必须看 MAC，分析前先确认每个 IP 的真实归属。

7.2 工具类

问题 根因 解决
Wireshark sshdump 用不了 远端无 dumpcap 远端 tcpdump -w - + SSH 流式接回本地
无法安装抓包工具 精简固件包管理器源为空 用固件自带的 tcpdump
SFTP 拉不了文件 dropbear 无 sftp 子系统 exec_command('dd if=...') 流式下载
-i any 抓包失败 某些内核不支持任意接口的混杂模式 指定真实接口名
pcap 尾部截断 kill 时缓冲区未写完 capinfos 会提示，通常可分析；必要时用 editcap 修复

7.3 业务/会话类

问题 现象 根因 解决
频道接口返回 302 → 超时页 Category.jsp 无限跳转 SessionTimeOut 会话已过期（抓包起点在认证之后） 覆盖完整开机流程重抓
DHCP 反复 NAK 机顶盒请求被拒 旁路抓包只看到片段，误判为业务退订 修正抓包点后一次成功

7.4 数据类（最隐蔽）

问题 现象 根因 解决
抓到 200 但无频道数据 频道接口响应体极小，ChannelCount: 0 服务器回了空壳，依赖前序会话；令牌失效或时序不对 确认认证链完整；必要时重抓
解析器“算出 0 频道” 用工具跑 pcap 得 0 包里根本没有数据，不是解析器的锅 先用工具自身函数端到端验证，确认包内是否有数据
假频道表 解析出大量“频道”，实为垃圾 PSI 未做 CRC 校验 加 CRC32==0 校验

通用教训：抓包类问题必须用端到端验证。
在没跑真实解析代码前，凭“预览片段”或“既有产物”反推包内容，极易得出错误结论。

7.5 认知类（代价最大）

误判 真相 教训
把人为改过的 MAC 当成“实物对应” 是用户自己改的，制造了假证据 看到地址吻合，先确认设备状态
把光猫发出的帧当成“机顶盒业务” 多个 IP 共享同一源 MAC（都来自光猫） 抓包必须带 -e 看 MAC；分析前确认每个 IP 的真实归属
凭印象判断运营商 地址段归属需查证 运营商判断不能凭印象
假设流量走 WAN 路由表一行就写明了走哪个接口 抓包前先读路由表

八、经验沉淀

8.1 通用方法论（可迁移到任何抓包场景）

A. 抓包点决策树（见 2.3）

B. 抓包前自检 Checklist

  1. ip -br link：目标口是否 UP 且有 carrier（别栽在 NO-CARRIER）；
  2. 若用网桥：brctl showmacs <bridge> 是否两条腿都学到 MAC；
  3. bridge-nf-call-* 是否全 0 / 未加载；
  4. 抓包机自己会不会抢答目标段的 DHCP（别干扰被测设备）；
  5. BPF 是否过窄（宁可全抓，离线筛）。

C. 分析流程（通用）

体检 → 谁在说话 → 按协议分组 → 锁关键流 → 切流导出 → 解析清单

D. “如果重来一次”的最短路径

  1. 先确认桥通（或 SPAN 起了）→ 2. 全抓覆盖完整开机 → 3. 找控制面里的“列表/配置”接口
    → 4. 切流导出 → 5. 解析成 m3u8。不再走“旁路试错”的弯路。

E. 三条铁律

  1. 抓不到单播 ≠ 工具问题，而是抓包点位置问题；
  2. 解析前必须先证明包里有数据（端到端验证）；
  3. PSI/section 解析没有 CRC 校验 = 输出不可信。

8.2 本项目专属经验

经验 说明
透明网桥可零成本替代 SPAN 软路由做 in-line 网桥，单播必然穿透
华为 CU 体系里 getchannellistHWCU.jsp 比 Category.jsp 更直接 后者可能因会话过期返回 302
认证链是“表单自动提交”串联 必须完整覆盖，缺一环即无数据
Authenticator 由机顶盒本地算出 无法离线复算，只能抓原包
一频道一组播地址 频道数 == 唯一组播地址数

9.2 交付层：从组播到 HTTP

channels.m3u8 里是 rtp://239.x.x.x:4120，这是 RTP over UDP 组播。
PC 播放器的处境：

限制 说明
组播不跨网段 播放器不在 IPTV 组播域内就收不到
多播路由未开 桌面系统默认不加入组播组
播放器兼容性 部分播放器对组播支持不稳

解决方式：在 IPTV 组播可达的设备上做转封装（RTP → HTTP 单播）：

rtp://239.125.2.66:4120  ──转封装──▶  http://<host>:<port>/rtp/239.125.2.66/4120
        （组播）                              （HTTP 单播，PC 可直接播）

关键前提：转封装程序必须运行在 IPTV 组播可达的设备上（通常是那台软路由），
跑在普通 PC/内网上则收不到组播，转出来也是黑的。

原则：只做 remux（-c copy）不做转码。IPTV 是 MPEG-TS，转码等于自找 CPU 瓶颈。

本次已具备该层能力（channels_http.m3u 由转封装工具生成），
但其部署细节属于另一主题，本文不展开。

十、时效性与复现边界

这一章决定了产物能用多久、能不能“重算”出来。

10.1 令牌有效期

  • 频道表与回看 URL 内嵌 session 令牌（播放参数中含 GuardEncType=2 的签名串）；
  • 有效期约 1 小时（实测 tokenExpiredTime = 抓包时间 + 1h）；
  • 过期后回看 URL 失效，需重抓。

10.2 为什么不能“算出来”

环节 能否离线复现 原因
频道表字段解析 :check_mark_button: 可以 纯文本解析，脚本可复跑
回看 URL 生成 :cross_mark: 不可以 accountinfo 是服务器签名的令牌
认证 Authenticator :cross_mark: 不可以 由机顶盒本地固件算出（一长串加密值），无法离线复算

结论：频道表不能“重构”，只能在机顶盒重新认证时“抓出来”。

10.3 刷新流程（令牌过期后）

1. 在正确的抓包点上开始抓包
2. 断电重启机顶盒（触发重新认证）
3. 确认认证链完整（isSucessed=true）
4. 导出频道表响应体
5. 重新解析 → 重新生成播放列表

刷新成本很低：抓包点配好后，全程约 6 分钟（一次完整开机窗口）。

附录 A：术语表

术语 含义
单播（Unicast） 一对一通信，只有收发双方能看到
组播（Multicast） 一对多，加入组播组的设备都能收到（IPTV 直播用这个）
广播（Broadcast） 一对全体，同一广播域内所有设备都收到
SPAN / 端口镜像 交换机把指定端口的流量复制一份到另一个端口
透明网桥 二层转发设备，对两端主机“不可见”，不做三层路由
IGMP snooping 交换机/网桥按需转发组播的优化，抓包时应关闭
DHCP 自动分配 IP 地址的协议（Discover→Offer→Request→ACK）
RTP / RTSP 实时传输协议 / 实时流控制协议（直播 / 回看）
MPEG-TS 数字电视传输流格式（IPTV 实际承载的内容）
PSI / PAT / PMT / SDT 传输流里的节目信息表；SDT 含频道名
FCC 快速频道切换（运营商侧加速手段，非所有运营商都提供）
FEC 前向纠错（抗丢包）
m3u8 播放列表格式（文本，逐行描述频道与地址）

B.4 命令速查（按场景分组）

环境前提见 3.4。占位符：<iface> 接口 / <bridge> 网桥 / X.pcap 文件 /
<N> 流号。加粗的为关键命令。

【抓包前】确认链路与抓包点

# 接口是否有载波（★ NO-CARRIER 是最常见的"抓不到"原因）
ip -br link show <iface>

# 网桥转发表：两条腿都要有外部 MAC（is local? = no）
brctl showmacs <bridge>

# 网桥 IGMP snooping 是否已关（应为 0）
cat /sys/class/net/<bridge>/bridge/multicast_snooping

# bridge-nf 三开关（全 0 或 NA 都算通过）
for f in iptables ip6tables arptables; do
  printf '%s = ' "$f"; cat /proc/sys/net/bridge/bridge-nf-call-$f 2>/dev/null || echo NA
done

# 抓包机自己是否在抢答 DHCP（应无 67 端口监听，避免干扰被测设备）
ss -lunp | grep ':67'

【抓包】执行与接回

# 本地抓包（路由器上直接执行）
tcpdump -i <iface> -nn -U -s 0 -w out.pcap "ip or arp"

# 远端抓 + 流式接回本地（-T 禁用伪终端，否则 pcap 会被 \r\n 污染）
ssh -T root@<router> "tcpdump -i <iface> -nn -U -s 0 -w - 'ip or arp'" > out.pcap

【分析】体检与流量构成

# ★ 体检：包数 / 时长 / 接口封装 / 哈希
capinfos X.pcap

# ★ 源 MAC 分布（目标设备必须出现）
tshark -r X.pcap -T fields -e eth.src 2>/dev/null | sort | uniq -c | sort -rn

# 协议分层（看是否含 mp2t = MPEG-TS）
tshark -r X.pcap -q -z io,phs 2>/dev/null

# 链路层 + IP 归属（判断每个 IP 的真实来源）
tshark -r X.pcap -c 5 -T fields -e eth.src -e eth.dst -e ip.src -e ip.dst 2>/dev/null

【分析】按协议细查

# DHCP 链（option.dhcp: 1=Discover 2=Offer 3=Request 5=ACK 6=NAK）
tshark -r X.pcap -Y "bootp" -T fields \
       -e frame.number -e ip.src -e ip.dst -e bootp.option.dhcp 2>/dev/null

# 全部 HTTP 请求（定位目标接口）
tshark -r X.pcap -Y "http.request" -T fields \
       -e frame.number -e ip.dst -e tcp.dstport -e http.request.method \
       -e http.request.uri 2>/dev/null

# 是否有 VLAN tag（空 = 无 tag）
tshark -r X.pcap -T fields -e vlan.id 2>/dev/null | sort -u

# 组播地址去重统计（实际有几路在跑）
tshark -r X.pcap -Y "udp && ip.dst==<mcast-prefix>/16" \
       -T fields -e ip.dst 2>/dev/null | sort -u | wc -l

# 某一路组播的源（谁在发）
tshark -r X.pcap -Y "udp && ip.dst==<mcast-addr>" \
       -T fields -e ip.src -e udp.srcport -e ip.dst 2>/dev/null | head -3

【定位】找关键流（不要硬编码流号）

# ★ 按 URI 关键字反查流号（换一份 pcap 流程不变）
tshark -r X.pcap -Y 'http.request.uri contains "<uri-keyword>"' \
       -T fields -e frame.number -e tcp.stream -e ip.dst -e http.request.uri 2>/dev/null

【核查】确认响应是否真有数据

# ★ 列出该流所有响应：状态码 / 长度 / 是否 gzip
#   长度极小且无 gzip = 空壳；有 gzip = 可能是真数据
tshark -r X.pcap -Y "tcp.stream==<N> && http.response" -T fields \
       -e frame.number -e http.response.code -e http.content_length \
       -e http.content_encoding 2>/dev/null

【导出】切流与导出对象

# 切出单条流
tshark -r X.pcap -Y "tcp.stream==<N>" -w _s<N>.pcap

# ★ 导出 HTTP 对象（自动解压 gzip）
tshark -q -r _s<N>.pcap --export-objects http,_o<N>

【解析】从导出体抽字段

# 统计频道总数
grep -c "CUSetConfig('Channel'" _o<N>/<file>.jsp

# 抽取频道名
grep -o "ChannelName=\"[^\"]*\"" _o<N>/<file>.jsp | head -5

# 抽取组播地址
grep -o "ChannelURL=\"[^\"]*\"" _o<N>/<file>.jsp | head -5

【校验】文件完整性

 # 校验哈希（与预期值比对，确认文件未损坏）
 sha256sum X.pcap
